# 续航与功耗

电池只有 **520 mAh**（规格见上游 `docs/hardware-design/specifications.zh_CN.md`）。
上游仓库**没有提供任何实测电流数据**，它的 `demo_low_power.c` 只演示了 RTC 定时器
唤醒的 light/deep sleep，并明确写着"不使用按键唤醒：仓库尚无板级唤醒电路证据"。
所以下面的量级是按数据手册估的，**不是实测**；真实数字请用本文最后一节的方法测。

## 电流花在哪

| 消耗源 | 量级（估算） | 说明 |
| --- | --- | --- |
| **LCD 背光 @100%** | **20–60 mA** | 绝对大头 |
| CPU @160 MHz（射频关） | 20–25 mA | 已降到 80 MHz，省约 8–10 mA |
| LVGL port tick | — | `ESP_LVGL_PORT_INIT_CONFIG()` 默认 5 ms，每秒唤醒 200 次 |
| UI 定时器 | — | 原来固定 200 ms |
| 按键 ADC 轮询 | — | ~50 ms 一次 |
| ST7789 控制器 | 1–5 mA | 常开（当前不熄屏） |
| CW2017 电量计 | µA | 忽略 |
| ES8311 音频 | 0 | 本应用**从不初始化**音频 |

## 已经做了的

1. **背光空闲管理**（`main/otp_power.c`）——30 秒无按键后降到 10%。**不熄屏**：
   变暗之后仍然一眼能看清验证码，这正是这张卡的用法——抬眼扫一下，而不是先按键再看。
   按任意键恢复全亮，且**不吞这次按键**（屏幕本来就看得见，吞掉只会显得迟钝）。
   同步页例外，它始终全亮——屏幕上那个 `FoloPass-XXXX` 正是要在浏览器里认的。

   代价要说清楚：不熄屏意味着背光永远在耗电，省下的只是"全亮 → 10%"那一段。
   若哪天愿意接受熄屏，把这块改回去能再省一截，但按键唤醒的吞键行为要一并恢复。
2. **CPU 160 → 80 MHz**。ESP32-C3 的 APB 固定 80 MHz，SPI 屏的 40 MHz 时钟不受影响。
3. **刷新周期跟着屏幕状态走**：全亮 200 ms、变暗 1 s。变暗时仍照常刷新——
   屏幕还看得见，验证码不能是停住的。
4. Wi-Fi 只在开机对时的十几秒里存在，之后 `esp_wifi_deinit()`；BLE 只在同步页存在。

## 刻意没做 deep sleep

两个理由，都不是"嫌麻烦"：

1. **会毁掉 TOTP 的时间精度。** `CONFIG_RTC_CLK_SRC_INT_RC`——深睡期间靠内部 RC
   振荡器计时。ESP-IDF 会用晶振校准它，但仍有 0.1~1% 的误差，反复长睡会累积到秒级。
   而这个项目的立场是"宁可不显示，也不给一个看不出错的码"。
2. **按键唤醒不可靠。** 三键共用 GPIO0 的电阻分压，电压窗口是
   `{0,150} {150,447} {447,1900}` mV（`bsp_pins.h`），而 ESP32-C3 的数字低电平阈值
   约 0.8 V——**第三个键最高只到 1.9 V，压不出低电平**。"按任意键唤醒"实际只有
   两个键管用。上游那句"尚无板级唤醒电路证据"是有道理的。

下一步若要继续省，方向是 **DFS + 自动 light sleep**（`CONFIG_PM_ENABLE` +
tickless idle，并放宽 LVGL port 的 5 ms tick）。注意一个坑：**USB 控制台连着时会
持有 PM 锁，插着线永远不会进 light sleep**，只有拔线用电池时才生效——很容易被误判成
"改了没效果"。这一条应当在拿到实测基线之后再做。

## 能续航多久

### 实测值

三轮实测，每轮取 141~143 分钟的稳定窗口（放着不动、不按键）：

| 配置 | 平均电流 | 满电续航（线性外推） |
| --- | --- | --- |
| PM 关闭，背光 10% | 45.0 mA | 11.6 小时 |
| PM 关闭，背光全熄（仅用于对照） | 38.8 mA | 13.4 小时 |
| **PM 开启（DFS + 自动 light sleep），背光 10%** | **13.5 mA** | **约 38 小时** |

**大头从来不是背光，是 CPU 没机会进 idle。** 注意第三行比第二行低得多：屏幕亮着
（10%）却比"屏幕全熄但不睡"还省 25 mA。这也是为什么先做那个熄屏对照是值得的——
它把力气从只值 6 mA 的方向上引开了。

开启 PM 那轮的整轮是 725 分钟（12.1 小时）后仍剩约 50% 电。

**这个 13.5 mA 要打折扣看**：电流降到这个量级后，每分钟只掉 0.04% 电，已接近电量计
的噪声底——四段分别是 13.5 / 11.6 / 12.0 / 16.8 mA，逐分钟速率的标准差占均值 34%
（前两轮只有 9%）。诚实的说法是 **13.5 ± 2 mA、续航 31~45 小时**。而且这是"完全不碰"
的待机值，每按一次键屏幕全亮 30 秒，日常使用会高一些。

两轮都收敛：10% 那轮分三段是 48.2 / 43.4 / 43.3 mA；熄屏那轮分四段是
39.4 / 39.9 / 40.6 / 35.3 mA，后半段逐分钟速率的标准差只有均值的 9%。

**结论一：背光不是大头。** 从 10% 到完全熄屏只省 **6.2 mA（占总功耗 14%）**，
续航 11.6 → 13.4 小时。为这 1.8 小时牺牲"抬眼即看"不划算，因此保留 10% 变暗。

**结论二：真正的大头是那 38.8 mA 的底噪。** 屏幕全黑、什么都不做，仍然接近 39 mA。
它来自 CPU 根本没机会进 idle（`ESP_LVGL_PORT_INIT_CONFIG()` 的 tick 是 5 ms，
每秒唤醒 200 次；按键 ADC 约 50 ms 轮询一次）、屏幕控制器自身，以及稳压器静态电流。

**结论三：原先的估算错得离谱**，值得记下来当教训。改动前我按数据手册估"多数时间
变暗"应是 20–34 mA，且认为背光占大头——实测 45 mA，且背光只占 14%。**这类估算
不能当决策依据，必须实测。**

### 开启 light sleep 踩到的三个坑

这三条缺一不可，缺任何一条的表现都是"开了 PM 但不对劲"，而且症状各不相同：

1. **背光 LEDC 的时钟源**（`components/bsp/src/bsp_display.c`）。默认 `LEDC_AUTO_CLK`
   在 C3 上会选中 APB，而 LEDC 驱动一旦用 APB 且开了 PM，就持有
   `ESP_PM_APB_FREQ_MAX` 锁——只要背光在跑，light sleep **根本进不去**，改了等于没改。
   必须显式选 `LEDC_USE_RC_FAST_CLK`。
2. **LEDC 通道的睡眠策略**。`ledc_channel_config_t.sleep_mode` 默认是
   `LEDC_SLEEP_MODE_NO_ALIVE_NO_PD`，即"进 light sleep 就停止输出"。芯片每秒睡醒上百次，
   于是**背光疯狂闪烁**。改成 `LEDC_SLEEP_MODE_KEEP_ALIVE`。
3. **GPIO 睡眠隔离**。`CONFIG_PM_SLP_DISABLE_GPIO` 为省 200~300 µA 会在每次自动睡眠时
   隔离**所有** GPIO，背光脚也被掐。用 `gpio_sleep_sel_dis(BSP_LCD_BL)` 单独排除。

### 还有一个会把你锁在门外的坑

**ESP32-C3 的 USB Serial/JTAG 不支持在 light sleep 下工作，唤醒后也不行**（ESP-IDF 的
Kconfig 原话）。开了自动 light sleep 而没开
`CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION`（默认关闭）的后果是：芯片第一次进睡眠，串口
就永久失联——日志断在开机 284 ms，**连 esptool 都连不上，没法再烧录**。

这个状态下唯一救回来的办法是 `esptool --before usb_reset`（USB 级复位，不依赖已死的
CDC 通道），成功率约 2/3，多试几次即可：

```bash
python -m esptool --chip esp32c3 --port <PORT> --before usb_reset \
    --after hard_reset write_flash --flash_mode dio --flash_size 8MB --flash_freq 80m \
    0x0 build/bootloader/bootloader.bin \
    0x8000 build/partition_table/partition-table.bin \
    0x10000 build/FoloToy-AI-Passport.bin
```

打开那个开关之后：**插着 USB 时持锁不自动睡**（串口与烧录正常），拔线用电池时才睡。
代价是所有功耗测量都必须拔线跑——放电记录器本来就是为此设计的。

### 再往下还能做什么

当前 13.5 mA 里，屏幕控制器与稳压器静态电流已占相当比例，继续压的空间有限。
真要再进一步，方向是熄屏（省 6 mA，但牺牲"抬眼即看"）或更激进的
deep sleep（本文档前面已说明为什么不做）。

### 实测（约 20 分钟）

固件自带放电记录（`main/otp_batlog.c`），**下次开机时把上一轮的记录打到串口**——
因为真正的放电测试必须拔掉 USB 跑，而那时串口没人听。

能做到 20 分钟出结果，靠的是满精度的电量读数：CW2017 的 SOC 寄存器**低字节是
1/256 %**（0.004%），而上游 `bsp_battery_soc()` 只返回高字节的整数百分比。本仓库
给 BSP 补了 `bsp_battery_soc_q8()`。差别是实打实的：按整数百分比，10 小时的电池要
6 分钟才跳 1%，得跑几小时才有可信斜率；按 1/256 %，十几分钟就够。

记录规格：每分钟一个点，环形保留最近 144 点（2.4 小时），每 5 个点落一次盘
（每分钟重写 870 字节的 blob 太磨 flash，掉电最多丢 5 分钟数据）。

```
1. 充满电（顶栏电量到 100%），拔掉 USB。
2. 放着别动 20~30 分钟。中途别按键——按了就是在测全亮功耗。
3. 插回 USB，复位一次，接串口看启动日志。
```

输出形如：

```
uptime_min,soc_percent,mv
0,98.44,4131
1,98.05,4118
...
===== 22 分钟掉 1.95%；平均 27.6 mA；按 520 mAh 线性外推满电约 18.8 小时 =====
```

想知道背光到底吃多少，就再跑一轮，中途每十几秒按一下键让它保持全亮，两条斜率一减
就是背光那一段。

**不要拿插着 USB 的运行时长当续航**——那时它在充电，SOC 只会上升，
设备会直接打印"电量没有下降（多半是插着 USB 在充电），无法估算"。
